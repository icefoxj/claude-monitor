# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Firmware for M5Stack devices that act as a desk status light for Claude Code. Claude Code hooks reach a host daemon, which sends one-line commands over USB serial; the device draws the matching icon (the cube keeps it upright as it is tilted, the tablet turns its whole page in 90° steps). Native **ESP-IDF 5.5** (C++/CMake/FreeRTOS), no Arduino, no PlatformIO, no Wi-Fi; the host side is three PowerShell 7 scripts (a daemon that owns the port and receives the hooks over HTTP, its installer, and a one-shot sender). Two boards, each a small ESP-IDF project on top of one shared component: the **AtomS3R** (ESP32-S3, 128×128 IPS display, BMI270 IMU), the first and reference board, which shows one icon; and the **Tab5** (ESP32-P4, 5" 1280×720 MIPI-DSI touch panel, BMI270, speaker, 32 MB PSRAM), which shows a tile per Claude Code session and a hook inspector. Both have prebuilt images in the releases (the Tab5 since 1.3.0).

`claude-code-status-monitor-atoms3r.md` is the original write-up (design rationale, icon geometry, hook configuration) — read it before non-trivial changes. The code has since moved past it on purpose: the waiting icon shows an exclamation mark instead of the word STOP, there is a blue question-mark sign for `AskUserQuestion`, there are `error` (red cross), `paused` (amber hourglass) and `compacting` (grey gear) states plus a subagent counter that gives the gear a satellite, the "look at the terminal" signs pulse on entry, the static icons rotate continuously with the tilt instead of in 90° steps, there is a `status` command, the hook set covers far more than the article's four events, the code is split into a component plus per-board projects instead of one `main.cpp`, a band around the icon carries overlays (elapsed-work ring, session dots, lost-link mark), the host pings the device and the screen dims/switches off on its own, the calibration can be stored in NVS at runtime, there are host tests and CI with a browser flasher, a second board (the Tab5) shows every session at once, and the Tab5 has three more themes (anime, LCARS, galactic). Do not "fix" those back toward the article's listing. The README's hooks section is the current reference for the host side, and `CHANGELOG.md` records what each release changed (keep it updated in the same commit as the change, under the next version).

Machine-specific notes (toolchain paths, COM port, antivirus) belong in `CLAUDE.local.md`, which is gitignored.

- `firmware/tab5/` — the ESP-IDF project for the M5Stack Tab5 (ESP32-P4): `main/main.cpp` is the multi-session view. `std::array<Slot, 6> slots` plus a `placeholder` slot; a `Slot` owns its PSRAM `M5Canvas`, `Icons`, `Ui` and `EventLog` (`place(size, x, y)` recreates the sprite when the size changes and calls `Icons::setSize`). `applyLayout()` (on session count change, rotation change, view change) hides every `Ui` (`setVisible(false)`), then either lays the grid (1 → 1×1, 2 → 2×1 or 1×2, 3–4 → 2×2, 5–6 → 3×2 or 2×3 by orientation) plus the usage tile when `hasUsage()` (the last cell; 7 cells → 4×2 or 2×4), or the detail page (icon column 560×720 in landscape with the inspector at (560,0); 720×560 in portrait with the inspector at (0,560)). Texts and icon share the tile through `textStyleFor(tileHeight)`: DejaVu40 with a 56 px band when the tile is ≥ 600 tall (one row), DejaVu24 / 40 px for ≥ 300, DejaVu18 / 32 px below; the icon gets `kIconScale` (0.80) of what is left (`min(width − 32, height − 2·band)`), and the group name band + icon + clock band is centred in the tile so the texts sit right against the icon (`Slot::nameY`/`clockY`). That is `placeIn(rect, band)` → `Placement` (icon size and position, the two rows' centre lines, `roomX`/`roomY`/`roomW`/`roomH`, the box the usage tile's bars take), used for the grid tiles, the usage tile and the detail column (`detailCol`); in the other themes it puts the rows `kRowInset` from the tile's top and bottom and the icon, `kAnimeIconScale` (0.96) of the room, centred between them (LCARS: right of the side bar), and the usage bars get the whole room. In those themes `drawTexts()` calls `themedTile` per tile (number, name, `look()` captions, the clock; a WaitingUser/Error tile blinks each redraw: the anime's number tag, the LCARS elbows, the galactic brackets) and the usage tile's rows, instead of the names and clocks. `drawTexts()` writes the name (white) above and the clock (`framesInState()/30` as mm:ss, light grey) below each visible tile once a second, and on every change; `drawInspector()` draws the detail slot's log. None of that is drawn on the panel: `composeTexts` draws it into `textCur`, one of two display-sized PSRAM canvases (`textLayerA`/`B`), over the `textRegions` that `applyLayout` lists (each tile but its icon square, as up to four rects from `addAroundIcon`; the whole usage tile; the detail column but its icon), and `drawTexts` then pushes only `changedRects(textCur, textPrev, ...)` (`screendiff.h`) through the display's clip rect and swaps the two, so `textPrev` is always what the panel shows there. `applyLayout` fills `textPrev` black along with the screen. Drawn straight on the panel, each row was erased and drawn again every second, and it flashed (worst with the LCARS elbows); now a second's tick sends the clocks' changed digits and nothing else. Anything else drawing over a text region (the saver, the usage page) must be followed by a layout, which they are. The usage tile (`usageShown`, `usageTile`, `usageBox`) uses the same bands as its row: "Claude usage" at the names' height, the bars in a box as tall as the icons and `4 * kTileGap` narrower than the tile, the age ("3 min ago") at the clocks' height; `drawUsageTile()` runs at the end of `composeTexts()` (once a second), its rows drawn by `drawUsageRows` straight into the text layer. A `usage` line that makes the tile appear or disappear sets `relayout` unless the screensaver is up (leaving it lays the grid out anyway); a tap on the tile opens the usage page (`View::Usage`: every `Ui` hidden, `pageCanvas` created at the display's size in PSRAM, `UsagePage::draw` every 10 s (`kPageRefreshFrames`: its texts change by the minute) and on each `usage` line, `drawTexts` skipped; the page goes to the display in 64-row bands (`kPushBand`, through the parent's clip rect): with the display turned a push reads the canvas a column at a time, and 720 rows 2560 bytes apart thrash the cache, so one 1280×720 push took 755 ms against 93 ms in bands, and the loop, blocked ~800 ms of every second, missed most taps. The 720×720 inspector and the 486 px icons do not need it; a tap or `view grid` returns, except a tap in the top-right corner (`usagePage.themeSwitch()`, a `UsageSwitch` from `usagepage.h`: the 56 px icon `drawThemeSwitch` draws in every theme's page header, one stripe per theme with the current one lit, the age moved left of it, and a 160×110 px tap area), which moves to the next theme (`switchTheme(nextAvailableTheme(...))`: classic, anime, LCARS, galactic) and stays on the page; `view usage` opens it, a `usage none` sends it back to the grid; `STATUS` says `view=usage`). `session` lines create/update slots (`applyState` → `Ui::apply`, beep on WaitingUser/Error when the tile is visible, `setSubagents`, `setToolRunning`), `session_end`/`session_clear` free them (`Slot::reset`), `event` lines go to the slot named by `session_id` (creating it if the event beat its session line); the aggregate words drive the placeholder, shown only while no slot is used. Touch: `wasClicked()` with `tile.contains(x, y)` opens the detail, any tap on the detail returns, a tap wakes an auto-off screen. Sound: `playAlert(state)` plays the active theme's `renderAlert` with `M5.Speaker.playRaw` (channel 0, stopping what plays; 32 kHz; rendered on first use into `alertSounds[theme][alert]`, kept because the speaker reads the buffer while it plays); for the classic theme it falls back to the two `M5.Speaker.tone` notes five frames apart (`Beep`/`tickBeep`), non-blocking. `switchTheme` plays the new theme's attention sound when the theme actually changes. Recordings: `firmware/tab5/sounds/<theme>-<attention|failure>.wav` (the whole folder is gitignored except its tracked `README.md`, so a source file dropped there to convert stays out too; never commit a recording, the films' and shows' sounds are their owners') are found by `main/CMakeLists.txt` at configure time, embedded with `EMBED_FILES`, and listed in a generated `monitor_sounds.h` (`kEmbeddedSounds`: theme, alert, start/end symbols, name; a `nullptr` name ends it) in the component's build directory; the folder is a `CMAKE_CONFIGURE_DEPENDS`, so adding or removing a file reconfigures on the next build. `loadRecordings()` at boot decodes each into `alertSounds[theme][alert]` (`AlertSound`: pcm, rate, recorded), which `playAlert` then plays in place of the synthesised one; the boot log names each recording or says why it was ignored. CI and releases have no recordings. The BMI270 drives `Orientation` (whole display turns in 90° steps); the icon itself is never tilted. `calibrate rot=N sign=S` means "N is the upright rotation right now": the offset is `orient.offsetFor(N, S)`, stored in NVS as `rotation`/`sign` (`offsetDeg` unused); `calibrate reset` → the compiled defaults, offset 3 and sign 1, which were verified on one unit (with the tablet on its stand gravity reads along +x, sector 0, and the upright display is rotation 3; with offset 1 every position came out upside down). USB Serial/JTAG transport with an 8 KB receive buffer, `LineParser(4096)`, 512-byte reads; `kFeatures = "events,touch,rotate,sessions,usage,theme"`. `theme <classic|anime|lcars|galactic>` goes through `switchTheme` (shared with the usage page's switch: sets the theme, stores it with `saveTheme`, sets `relayout`, which also leaves the saver) and answers with `STATUS` (`theme=`); a bad or unavailable name answers `ERROR theme: ...`; the stored theme is loaded at boot right after the calibration. Like `view`, it does not feed the link watchdog. `view grid` / `view detail <id>` do what a tap does (`view detail` alone opens the only tile there is, the placeholder included); `screenshot` applies a pending layout, draws texts and inspector, then calls `dumpDisplay` through `writeAll`, which writes in 1 KB pieces and retries for up to 2 s per piece: `usb_serial_jtag_write_bytes` refuses an item larger than its TX ring buffer (2 KB here) outright instead of queueing part of it, which silently dropped every 5 KB row the first time. A 1280×720 capture is 3.7 MB of base64 and takes about 17 s, during which the loop is blocked. `sessions <codes>` puts the session dots on the placeholder (the only tile that ever shows them on this board). `status`, `version`, `screenshot` and `view` do not feed the link watchdog. Screensaver: `saver` (a global `monitor::UsageSaver`) is fed by `usage` lines; the loop enters it (`enterSaver`: every `Ui` hidden, `saver.enter`) when the aggregate of the visible tiles has been Idle or Off for `kSaverFrames` (10 min, counted in real frames in the tick block) with the link not lost, at `kSaverBrightness` (70); a tap, `woke` (a state change), any `relayout` (a new tile, a rotation) or a lost link leaves it (`leaveSaver` sets `relayout` and resets the count); `view saver` enters it at once; `drawTexts`/`drawInspector` and the tiles' drawing are skipped while it runs, and `screenshot` dumps it as is. There is no idle switch-off any more on this board, only the 30-minute no-host one. The main task stack is 48 KB (`CONFIG_ESP_MAIN_TASK_STACK_SIZE` in `sdkconfig.defaults`): the default 3.5 KB overflowed ("Stack protection fault", `MCAUSE 0x1b`) when the saver handed the screen back, 16 KB overflowed at boot in the anime theme because M5GFX's `VLWfont::drawChar` `alloca`s the whole glyph (28 KB for a 192 px kanji), and keep big objects out of `app_main`'s frame (the saver is a global for that reason). `STATUS` reports the aggregate state of the visible tiles, `sessions=` as one code letter per tile, `rot=` (display rotation in effect), `angle=` (gravity direction in the panel plane), `offset=` (sector-0 rotation), `sector=`, `tiles=`, `view=grid|detail|usage|saver`, `screen=saver` while it runs, `usage=` (the percentages, or `-`), `theme=`. `sdkconfig.defaults`: `esp32p4`, 16 MB QIO flash, PSRAM 200 MHz + `CONFIG_IDF_EXPERIMENTAL_FEATURES`, L2 cache 256 KB, `CONFIG_MONITOR_ANIME_THEME`, and `partitions.csv` (the single-app-large layout with a 4 MB app; the image is 1.6 MB with the fonts, more than the stock 1.5 MB partition; NVS stays at `0x9000`). Runs on hardware (see Gotchas for what was verified).

- `firmware/atoms3r/` — the ESP-IDF project for the AtomS3R: `CMakeLists.txt` adds `../../components` via `EXTRA_COMPONENT_DIRS`; `main/main.cpp` holds only board wiring (canvas size, boot rotation and IMU calibration constants, `usb_serial_jtag` transport, `status` reply formatting, `BtnA` screen toggle, the 33 ms loop); `sdkconfig.defaults` carries the two non-defaults (target `esp32s3`, 8 MB flash); `dependencies.lock` pins the M5Unified/M5GFX versions and is tracked. Build artefacts (`build/`, `managed_components/`, `sdkconfig`, `.vscode/settings.json`) live here and are gitignored; `.vscode/c_cpp_properties.json` and `launch.json` are tracked.
- `host/Monitor-Daemon.ps1` — the host daemon (PowerShell 7): owns the serial port, receives Claude Code hook events as HTTP POSTs on `http://localhost:47831/hook`, keeps one state per session, sends the device the most urgent one, logs to `%LOCALAPPDATA%\claude-monitor\daemon.log`. `host/Install-MonitorDaemon.ps1` registers it as a logon scheduled task ("claude-monitor daemon") whose action is `conhost.exe --headless pwsh.exe … -File Monitor-Daemon.ps1`, so no window exists to be closed (see Gotchas). `host/Send-ClaudeState.ps1` is the one-shot sender: through the daemon's `/state/<state>` when it runs, else straight to the port; it is also what the no-daemon command-hook variant calls.
- `claude-monitor.code-workspace` — multi-root workspace (repo + `firmware/atoms3r` + `firmware/tab5`) so the ESP-IDF extension finds a project.
- `tests/host/` — host tests for `protocol.cpp`, `tilt.cpp`, `orientation.cpp`, `usage.cpp`, `sounds.cpp` and `screendiff.cpp` (the usage line with the page's fields, the pace, the clock texts; `test_core.cpp`, plain C++17, a `CHECK` macro, exit code = failures); `run.sh` (Linux/macOS/CI, `g++`) and `run.ps1` (Windows, MSVC via `vswhere`, else `g++`). The icons and `Ui` need `M5Canvas` and are not covered.
- `.github/workflows/build.yml` — CI: host tests + a build of each board (matrix `atoms3r`/`esp32s3` and `tab5`/`esp32p4`, `espressif/esp-idf-ci-action`, ESP-IDF v5.5) on every push/PR, each board's four images as an artifact; on a `v*` tag, both boards' assets attached to the release (`softprops/action-gh-release`, which creates the release if it does not exist) and the web flasher deployed to GitHub Pages; `workflow_dispatch` with the `release` input republishes the flasher from an existing release's assets. `docs/index.html` is that page (ESP Web Tools; CI puts `manifest.json` and the AtomS3R's **three parts** next to it, and replaces every `__VERSION__`, including the file names in the Tab5's esptool line). The flasher carries the AtomS3R only; the Tab5 is flashed with esptool (bootloader at `0x2000`). ESP Web Tools 10.4 bundles an ESP32-P4 loader, so a second `builds` entry with `chipFamily` `ESP32-P4` would serve the Tab5 from the same button, but that has not been tried in a browser yet. The manifest deliberately lists bootloader/partition table/app at their offsets rather than the merged image: the merged image pads the gap over the NVS partition and would erase a stored calibration.
- `CHANGELOG.md` — one section per release. `.clangd` (strips `-f*`/`-m*` so clangd can read the xtensa compile database) and `.devcontainer/` (the stock `espressif/idf` image; inside it, work from `firmware/atoms3r` or `firmware/tab5`) are the only other tracked files besides the article, the README and the license.

A new board = a new `firmware/<board>/` project with its own `sdkconfig.defaults`, `main/main.cpp` and calibration constants, plus a section in the README. Anything that would be duplicated between boards belongs in `monitor-core`.

## Toolchain and commands

`idf.py` only exists inside an activated ESP-IDF environment: the VS Code command **ESP-IDF: Open ESP-IDF Terminal**, the "ESP-IDF PowerShell" Start Menu shortcut on Windows, or `export.ps1` / `export.sh` from the ESP-IDF directory. Never prefix `idf.py` with `bash` on Windows (it hands the line to WSL). Keep the project path free of spaces. Run from the board's project directory, or pass it with `-C`:

```
cd firmware/atoms3r
idf.py set-target esp32s3     # only on a fresh checkout or after fullclean
idf.py build                  # first build downloads M5Unified/M5GFX into managed_components/
idf.py -p COM5 flash          # esptool over the USB-C virtual serial port (/dev/ttyACM0 on Linux)
idf.py -p COM5 monitor        # Ctrl+] to exit. CLOSE IT before sending protocol commands: the port is exclusive on Windows
idf.py menuconfig
idf.py fullclean
```

The Tab5 project is `firmware/tab5` with `idf.py set-target esp32p4`; its first build downloads its own `managed_components/` and compiles the whole IDF for the P4 (minutes). Everything else is the same.

`idf.py flash` rebuilds first. A rebuild can take minutes on a machine whose antivirus scans the toolchain, so run it with a long timeout. **The daemon owns the port while it runs**: before `flash`, `monitor` or any direct serial access, `Invoke-RestMethod -Method Post http://localhost:47831/release` (the port is free for 120 s, then the daemon reconnects and re-sends the current state; `POST /reconnect` reconnects at once). Without the release, flashing fails with "port is busy". First-ever flash of a board may require holding the side reset button ~2 s to enter download mode. The VS Code extension is configured with `idf.flashType: JTAG` (OpenOCD, `board/esp32s3-builtin.cfg`), so **ESP-IDF: Flash your Project** goes over the S3's built-in USB-JTAG instead; both paths use the same cable. The binary is `build/claude-monitor-atoms3r.bin` (`firmware/tab5/build/claude-monitor-tab5.bin` for the Tab5).

Manual end-to-end test (device flashed, monitor closed):

```powershell
.\host\Send-ClaudeState.ps1 -State processing -PortName COM5   # also: waiting_user | question | error | paused | compacting | idle | off | subagent_start | subagent_stop
```

Reading the device's replies: with the daemon running, `Invoke-RestMethod http://localhost:47831/serial/status` returns the `STATUS` line, `Invoke-RestMethod http://localhost:47831/version` the `VERSION` line parsed (hardware model, firmware version, uptime), and `GET /status` shows sessions and the last state sent. Without the daemon, open `System.IO.Ports.SerialPort` on the port at 115200 with DTR/RTS off, `WriteLine("status")`, then `ReadLine()` until a line containing `STATUS` — boot-log fragments may precede it. Note that in a session where the hooks are active, every tool call that prompts for permission sends `waiting_user` before it runs, so a status read taken from Claude Code will usually report that state rather than the one you set a moment earlier; the daemon log shows the exact sequence.

Tests: `.\tests\host\run.ps1` (Windows) or `bash tests/host/run.sh`; they take seconds and need no ESP-IDF. Run them after touching `protocol.*` or `tilt.*`, and add a `CHECK` for every new protocol word or parsing rule. There is no linter. `.clangd` (repo root) strips `-f*`/`-m*` flags so clangd can parse the xtensa compile database; `firmware/atoms3r/.vscode/settings.json` (gitignored, machine-specific: ESP-IDF setup, clangd binary and `--compile-commands-dir`, COM port) points it at `firmware/atoms3r/build`. `firmware/atoms3r/.vscode/c_cpp_properties.json` is tracked and carries an absolute `compilerPath`.

## Releasing

A version is an annotated tag `vX.Y.Z` on `main` plus a GitHub release with four images per board (`claude-monitor-<board>-vX.Y.Z{,-merged,-bootloader,-partition-table}.bin`, produced by `tools/collect-images.sh`; releases up to 1.2.0 used plain `bootloader.bin` / `partition-table.bin` for the AtomS3R), and CI does the build for every board in the matrix: write the `CHANGELOG.md` section, commit, `git tag -a vX.Y.Z`, push the tag, wait for the `build` workflow (`gh run watch`), which attaches the images to the release for the tag (creating the release if none exists) and deploys the web flasher; then put the notes in with `gh release edit vX.Y.Z --title "claude-monitor X.Y.Z" --notes-file notes.md`. Notes follow the existing releases (new on the device, new on the host, flashing without the toolchain, built with). Check the `fw=` the CI image reports (the workflow log prints the embedded version) before flashing it to the reference unit.

Local fallback, same result by hand: the version embedded in the binary (`esp_app_desc`, printed as `App version:` in the boot log and as `fw=` in `STATUS`) is `git describe --tags --dirty`, **captured when CMake configures**, not on every build: tag first, make sure the tree is clean, then `idf.py reconfigure build`. A plain `idf.py build` after tagging keeps the previous string (the 1.1.0 assets had to be rebuilt for exactly that reason). Then, in the activated ESP-IDF shell (its venv provides `esptool`):

```powershell
cd firmware/atoms3r
python -m esptool --chip esp32s3 merge_bin -o claude-monitor-atoms3r-vX.Y.Z-merged.bin --flash_mode dio --flash_freq 80m --flash_size 8MB 0x0 build/bootloader/bootloader.bin 0x8000 build/partition_table/partition-table.bin 0x10000 build/claude-monitor-atoms3r.bin
Copy-Item build/claude-monitor-atoms3r.bin claude-monitor-atoms3r-vX.Y.Z.bin
gh release create vX.Y.Z --title "claude-monitor X.Y.Z" --notes-file notes.md claude-monitor-atoms3r-vX.Y.Z-merged.bin claude-monitor-atoms3r-vX.Y.Z.bin build/bootloader/bootloader.bin build/partition_table/partition-table.bin
```

The flash arguments come from `build/flasher_args.json`. For the Tab5 the same recipe needs `--chip esp32p4`, `--flash_size 16MB` and the bootloader at `0x2000` (the ESP32-P4's offset, not `0x0`); simpler, for either board, run `bash tools/collect-images.sh firmware/<board> <board> vX.Y.Z dist` from Git Bash in the activated shell, which reads all of that from `flasher_args.json` and names the four files as CI does. `gh release upload vX.Y.Z --clobber <files>` replaces assets on an existing release. GitHub Pages is set to the "GitHub Actions" source (`gh api repos/icefoxj/claude-monitor/pages` shows `build_type: workflow`), and the `github-pages` environment has custom deployment-branch policies for `main` and the tag pattern `v*` (without the `v*` entry a tag build fails with "not allowed to deploy to github-pages due to environment protection rules"). The flasher page is republished by a tag build or by `gh workflow run build.yml -f release=vX.Y.Z`.

## Architecture

**Serial protocol** (`protocol.h`). One command per line, `\n`-terminated. State commands: `processing`, `waiting_user`, `question`, `error`, `paused`, `compacting`, `idle`, `off`. Counter commands: `subagent_start` / `subagent_stop`. Flag commands: `tool_start` / `tool_stop` (a tool process is running; `STATUS` shows `tool=`). `sessions <codes>`: the live sessions as one letter each (`sessionCode()`: p w q e h c i), most urgent first, up to 8 used. `ping`: heartbeat. `calibrate rot=<0-3> sign=<1|-1> offset=<deg>` (any subset) or `calibrate reset`, parsed by `parseCalibration` into a `CalibrationRequest`; a bad field rejects the whole line and the board answers `ERROR calibrate: …`. And `status`, answered with one `STATUS state=… subagents=… rot=… angle=… ax=… ay=… az=… fw=… board=… sign=… offset=… sessions=… link=… work=… screen=…` line (`fw` is `esp_app_get_description()->version`, `link` is `unarmed|ok|lost`, `work` is seconds of processing this turn, `screen` is `on|dim|off`). And `version`, answered with one `VERSION board=… model=… chip=… rev=… cores=… flash=… fw=… idf=… m5unified=… protocol=… project=… built=… sha=… uptime=… reset=…` line (`board` = the build's `kBoard`, `model` = `boardModelName(M5.getBoard())`, so a firmware on the wrong module shows up; `protocol` = `kProtocolVersion`, bump it when words are added). The board also sends the `VERSION` line once at boot, right after `usb_serial_jtag_driver_install`, through the driver: an `ESP_LOGI` of it was lost, because the console's secondary USB channel drops long lines when the host is not draining the FIFO. Neither `status` nor `version` feeds the link watchdog. `VERSION` carries `features=` (comma list; `-` for none): a capability the host checks before sending anything optional. Protocol 3 adds `event <name>\t<key>=<value>\t…` (`parseEventLine` → `HookEvent {name, fields}`, `HookEvent::find`): a whole hook event, sent only to a device whose features include `events`, because a line can be a few KB and the AtomS3R's 1 KB receive buffer and 64-byte `LineParser` would choke on it (its parser now drops an over-long line whole, newline included, so nothing leaks through as a stray word). Protocol 5 adds the per-session lines for boards with `sessions` in features: `session <id>\tlabel=…\tstate=…\tsubagents=…\ttool=…\tproject=…\troot=…` (same tab format, parsed with `parseEventLine`, the state with `parseState`), `session_end <id>`, `session_clear`. Protocol 6 adds two queries for documentation and debugging: `screenshot` (the board dumps its display as `SCREENSHOT`/`ROW`/`END` text lines, see `screenshot.h`; the AtomS3R answers `ERROR screenshot: not supported on this board`, its SPI panel is not read back) and `view grid` / `view detail <id>` (what a tap does on the Tab5; the cube ignores it). Protocol 7 adds `usage <source>\tage=<s>\tlimit=<label>|<percent>|<seconds to reset>|<severity>...\tsplit=<label>:<percent>|...` (`parseEventLine` underneath, one `limit=` per limit, at most 4; `split=` the week by app, at most 5 shares), sent only to a board that lists `usage`; `view saver` starts the Tab5's screensaver. Protocol 8 adds the usage page's fields to the same line, all optional and skipped by older boards' `parseUsage`: `now=<unix>|<UTC offset s>`, `windows=<s>|<s>...` (in limit order), `plan=<name>|<status>|<since unix>`, `extra=<on|off|full>|<used>|<limit or ->|<currency>`, `history=<start unix>|<step s>|<percent>,<percent>,...` (empty = no reading), `project=<name>|<week %>|<today %>` (up to 6), and `view usage`. Protocol 9 adds `theme <classic|anime|lcars|galactic>` (`Command::Theme`, the argument checked with `parseTheme`), for boards with `theme` in features; the cube answers `ERROR theme: not supported on this board`. When adding a word, bump `kProtocolVersion` and add a `CHECK` in the host tests. `parseCommand` splits the first word from the argument (`ParsedCommand::arg`); `LineParser` strips trailing `\r`/spaces and discards lines over 64 bytes; unknown words are ignored. The transport is the board's: on both boards it is the chip's native **USB Serial/JTAG** peripheral (the ESP32-S3's on the AtomS3R, the ESP32-P4's on the Tab5's USB-C; no UART bridge chip; opening the port does not reset the board), and the `STATUS` reply is written straight through that driver so it does not depend on where the ESP-IDF console is routed. The hook → state mapping (which events, which `Notification` types and `StopFailure` error types go where) lives in `Map-Event` in `host/Monitor-Daemon.ps1` and is documented as a table in the README's hooks section; the no-daemon variant expresses the same mapping as matchers in `settings.json`. When a state is added, update `Map-Event`, the README table, the no-daemon JSON and `Send-ClaudeState.ps1`'s `ValidateSet`. There is no hook event for the moment a permission is approved; the daemon infers it from the tool's process starting (see Host daemon), and without that `waiting_user` lasts until the approved tool's `PostToolUse`.

**Host daemon** (`host/Monitor-Daemon.ps1`). `~/.claude/settings.json` has one identical HTTP hook (`{"type": "http", "url": "http://localhost:47831/hook", "timeout": 2, "headers": {"X-Claude-Project": "${CLAUDE_PROJECT_DIR}"}, "allowedEnvVars": ["CLAUDE_PROJECT_DIR"]}`) for the fourteen events of interest (SessionStart, UserPromptSubmit, PreToolUse for every tool, PostToolUse, PostToolUseFailure, PostToolBatch, Notification, Stop, StopFailure, PreCompact, PostCompact, SubagentStart, SubagentStop, SessionEnd); the daemon reads `hook_event_name`, `session_id` and the event's detail fields. Per session it keeps `state`, `subagents`, `last`; the device gets the highest-priority state among live sessions (`$Priority`: error 6 > waiting_user = question 5 > paused 4 > compacting 3 > processing 2 > idle 1 > off 0, ties → most recent), sent only on change, plus `subagent_start`/`subagent_stop` deltas to keep the device's counter equal to the sum over sessions, plus `sessions <codes>` when the code string changes (`Sync-Device`). `SessionEnd` removes the session; the last one leaving sends `off`; sessions silent for `SessionTimeoutMinutes` (240) expire. **Compaction end**: `PreCompact` keeps the state it interrupted (`beforeCompact`), and a `SubagentStop` while `compacting` with no subagent counted restores it: the compaction runs as a subagent that sends `SubagentStop` but never `SubagentStart` (64 stops vs 51 starts in the logs). Since late October 2026 Claude Code also compacts a session left idle, 54 minutes after its `Stop` (seen on every idle session, presumably before the 1-hour prompt cache expires: `PreCompact` auto, the subagent's stop 55–125 s later), and sends that compaction's `PostCompact` only with the next `UserPromptSubmit`, hours later; before this rule the tile showed the grey gear all that time. Mid-turn and `/compact` compactions send `PostCompact` within a second of the stop, so nothing changes for them. `Expire-Sessions` also restores the state after `CompactTimeoutMinutes` (10) compacting with no event, and housekeeping now always calls `Sync-Device` (it sends only changes). **Approval detection**: on a session's first hook (or when its known process is gone) `Resolve-ClientPid` reads the request's TCP connection (`Get-NetTCPConnection -LocalPort <client port> -RemotePort 47831`, only valid while the request is being handled) to learn the session's `claude.exe` PID; `Update-ProcessTree` then diffs snapshots of the process table: `[ProcSnap]::Take(pids)` is a C# helper compiled with `Add-Type` at start (`Initialize-ProcessSnapshots`, Windows only) that calls `NtQuerySystemInformation(SystemProcessInformation)` and returns only the entries whose pid or parent pid is a session's (about 20 ms for 700 processes; x64 struct offsets). The main loop takes one every 500 ms while a session with a PID is `waiting_user` or had a hook in the last 5 s (a tool's process is about to appear), every 2 s otherwise. A child of a session's PID (not `conhost.exe`) that was not in `tools` (pid → name) is a tool starting: while the session is `waiting_user` that flips it to `processing` (`Note-ToolStarted`); a pid in `tools` that is gone is a tool that ended; the session PID missing marks it `dead` and `Expire-Sessions` drops it (the transcript-mtime heuristic only applies to sessions without a PID). The first snapshot after a session's PID becomes known (`seeded` false) only records the children already running, so a background tool is never taken for an approval. **Do not go back to WMI** `__InstanceCreationEvent` polling on `Win32_Process`: the arbitrator keeps whole instances for a polling query within `PollingMemoryPerUser` (5 MB), so with a few hundred processes (an ESP-IDF build) the subscription is cancelled silently and new ones fail with "Quota violation", and the flood of events before that stalled the daemon for minutes with the hooks timing out. `Sync-Device` sends `tool_start`/`tool_stop` when "the shown session has a live tool process" changes (`deviceTool`, reset like subagents), and ends with `Send-SessionLines`: for a device with `sessions` in features, `session_end` for ids it had that are gone, then one `session` line per live session whose line changed (`Format-SessionLine`, cached in `deviceSessionLines`; `Get-SessionLabel` appends `#n` when several live sessions share a project, numbered by `first`), starting with `session_clear` on a forced sync. `Process-Hook` sends the event line only after `Sync-Device`, so a new session's tile exists before its first event; ignored events send it directly. `PostToolUse`/`PostToolUseFailure` purge dead tool PIDs the events have not reported yet, and `subagent_start`/`stop` from a waiting session also mean approval. **Plan usage** (for the Tab5's screensaver): `$script:usage` (ordered, key → label, percent, `resetsAt` as `DateTimeOffset`, severity) is filled by `POST /statusline` (`Set-UsageFromStatusLine`: `rate_limits.five_hour` / `seven_day` → keys `session` / `weekly_all`; the answer is the status line text, `Format-StatusLineText`) and, with `-AccountUsage`, by `Start-UsagePoll` / `Complete-UsagePoll` every `UsagePollSeconds` (300): an `HttpClient.SendAsync` GET of `https://api.anthropic.com/api/oauth/usage` (headers `Authorization: Bearer <claudeAiOauth.accessToken from CredentialsPath>`, `anthropic-beta: oauth-2025-04-20`), picked up by the main loop when the task completes, so the loop never blocks; `Set-UsageFromAccount` reads the answer's `limits` list (`kind` session / weekly_all / weekly_scoped with `scope.model.display_name`, `percent`, `resets_at`, `severity`), else `five_hour`/`seven_day.utilization`. That endpoint is undocumented (verified 2026-10-22); 429 backs off 15 min, an expired token waits for Claude Code to refresh the file, the token is never logged. The status line is the documented source, but the VS Code extension does not run status lines (tested: no call in 60 s with `refreshInterval` 10), hence the poll. `Send-Usage` (every 5 s from the loop, after each update, forced after a reconnect via `deviceUsageKey = $null`) drops windows whose reset has passed and sends `Format-UsageLine` when the content changed or new numbers are 5 min newer than the device's; `Set-UsageFromAccount` also keeps `seven_day_breakdown.rows` (percent > 0) as `$script:usageSplit`, sent as `split=` (the status line has no such data). `GET /usage` and `/status` show `Get-UsageObject` (`week_by_app` included). **Usage page data**: `Format-UsageLine` also sends `now=` (the host's clock and UTC offset), `windows=` (`window` per entry: 5 h for the session, 7 d for the weeks, `Get-UsageWindow`), `plan=` (`$script:usagePlan`: `Get-PlanName` from the login's `subscriptionType`/`rateLimitTier` at each poll until `Complete-ProfilePoll` has read `GET /api/oauth/profile`'s `organization` (type, tier, `subscription_status`, `subscription_created_at`), every six hours through the same `Send-AccountRequest`), `extra=` (`Get-ExtraUsage`: the answer's `spend` with minor units and exponent, else `extra_usage`; only the disabled form has been seen, `user_disabled` true), `history=` (`Format-UsageHistory`: the weekly limit at each hour since its window started, the last reading of that window (matched by reset time, ±90 min, since the account's reset jitters by milliseconds) at most 3 h older, else empty) and `project=` (`Update-ProjectUsage`). The readings are `$script:usageHistory`, appended by `Add-UsageReading` (from both sources) when the weekly percentage changes or an hour after the last one, and kept in `UsageHistoryPath` (`usage-history.jsonl`, 35 days); with no file the daemon seeds it from the `device <- usage` lines of `daemon.log`/`.1` (`Import-UsageHistoryFromLog`). The projects come from `TranscriptUsage`, C# compiled with `Add-Type` like `ProcSnap` (System.Text.Json): `ScanAsync(TranscriptsPath, 8)` on a pool thread every 60 s reads what was appended to every `*.jsonl` under `~/.claude/projects` written in the last 8 days (offset per file, `FileShare.ReadWrite`), parses only lines with `"type":"assistant"`, counts each `message.id` once at its largest usage, weighs the tokens like the API's relative prices (input 1, cache write 1.25 for 5 min / 2 for 1 h, cache read 0.1, output 5; Sonnet 0.6, Haiku 0.2) and buckets them per project folder and hour; the folder's root is the first `cwd` of a session's own file (not a subagent's, and not later lines: `cwd` follows `cd`). About 3 s for 1.7 GB the first time, ~20 ms after. `Update-ProjectUsage` splits the weekly percentage times Claude Code's share of `split=` (else all of it) by those weights, top five plus `other`; `-NoProjectUsage` turns the reader off. Send-Usage's change key includes all of it; the logged line shows `history=...`. **Claude Desktop**: its Code tab fires the same hooks (it reads the same settings), so nothing is needed there; Cowork and scheduled tasks fire none, so with `-DesktopNotifications` the daemon reads the app's Windows notifications: `Initialize-DesktopWatch` compiles `DesktopToasts` (C#: `sqlite3_*` from the system's `winsqlite3.dll` opening `%LOCALAPPDATA%\Microsoft\Windows\Notifications\wpndatabase.db` read-only, rows of `Notification` joined to `NotificationHandler` whose `PrimaryId` is `Claude%!Claude` (Store app) or contains `AnthropicClaude`; `ForegroundImage()` through `GetForegroundWindow` + `QueryFullProcessImageNameW`) and takes what is there as seen, except the last five minutes. `Update-DesktopToasts` runs every 3 s (about 10 ms): each new notification's `<text>` nodes become an event line (`DesktopNotification`, title, body) and, when they match `approv|permission|needs? your|...`, an entry in `desktopWait`; `Sync-DesktopSession` keeps a pseudo-session `claude-desktop` (project "Claude Desktop", pid 0, so the process watching ignores it) in `waiting_user` while `desktopWait` is not empty, else `idle`, and removes it `DesktopLingerMinutes` (10) after it went idle. A wait ends when its notification leaves the database (clicked, dismissed), after `DesktopWaitMinutes` (30), or when the Claude window (`\WindowsApps\Claude_` or `\AnthropicClaude\` in the image path) has been in front for 3 s, since Windows never says the notification was acted on. Seen live: "Scheduled task needs your approval" toasts; a test toast can be posted under the app's AUMID from Windows PowerShell 5.1 (`ToastNotificationManager.CreateToastNotifier('Claude_pzs8sxrjxfjjc!Claude')`) and removed through `History.Remove`. Chats have no live signal at all. Everything degrades to hooks-only when the helper or the PID lookup is unavailable (`process_watch` and `process_pids` in `/status`). The main loop sends `ping` every `PingSeconds` (30) while the port is open. The port is reopened every 2 s when lost; on (re)connect the daemon asks `version` first (`Read-DeviceInfo`, kept as `device_info` in `GET /status`, also served fresh by `GET /version`) and then re-sends everything (state, subagents, sessions, a ping). The session's project comes from the `X-Claude-Project` request header (the hooks send `${CLAUDE_PROJECT_DIR}` with `allowedEnvVars`; `cwd` is not used when the header is there, because it follows the shell's `cd`), falling back to the first `cwd` of the session's transcript (`Get-TranscriptRoot` on the payload's `transcript_path`, the first MB, once per new session), then to the first event's `cwd`. The header arrived empty for every session checked on 2026-11-03 (the log line `session <id>: root ... (from header|known|transcript|cwd)` says which source was used), so in practice the transcript names the tiles; before that fallback a daemon restarted mid-session named a tile after whatever subfolder the shell was in (`memory`, `src`). The name is the root's folder name unless `projects.json` (`-ProjectsPath`, `{ "root": "name" }`, reloaded by housekeeping when its mtime changes) says otherwise (`Get-ProjectName`). Every hook, mapped or ignored, also becomes an `event` line (`Format-EventLine`: `summary=<tag>`, `project=`, `project_root=`, then every top-level field in payload order, objects flattened one level, values one-lined and cut at `EventValueMax` 160, line capped at 3800) kept in a 50-entry ring for `GET /events` and written to the port only if `device_info.features` contains `events` (`Send-Event`); `-LogEvents` appends the raw payload as JSON lines to `EventLogPath` (`hooks.jsonl`, rotated at 20 MB). The port is opened with UTF-8 encoding so those lines survive. `POST /release` closes the port for a flash window; `POST /theme?name=classic|anime|lcars|galactic` sends `theme <name>` and returns the reply; `POST /calibrate?rot=&sign=&offset=|reset=1` composes the `calibrate` line and returns the device's reply (`Send-SerialCommand` waits for `STATUS` or `ERROR` after `status` and `calibrate`). `Send-ClaudeState.ps1` must always `exit 0` because hook exit code 2 blocks Claude Code, and it retries a busy port for the no-daemon case.

**Rendering** (`icons.h`). `Icons` draws into a square 16-bpp `M5Canvas` supplied by the board (128×128 = 32 KB internal RAM on the AtomS3R). A frame is composed by `Ui::render`: one icon call (which clears the canvas), then the overlays, then `Icons::push()` (`pushSprite` at a configurable origin) — the icon functions themselves do not push, and nothing draws straight to `M5.Display`, which flickers. Icons are procedural (triangle fans, `thickLine` = oriented rect + two round caps, `thickArc` = polyline of those, one segment per ~6°), no bitmaps. The overlays live on a band of radius 60 (128-space), just outside the icons' 58: `ring(angle, fraction, lap)` grows clockwise from the top (lap 0 yellow, 1 amber, 2 red, each over the full ring of the previous lap, ≥3 full red); `sessionDots(angle, codes)` puts one 3.5-radius dot per code along the bottom, 10° apart, coloured by state (w and e both red) with a black outline so they read over the ring; `linkLost(angle)` is a hollow grey circle at the top; `toolMark(angle)` is a blue disc reading "EXT" in white at the bottom-right corner (centre 46 units out along the diagonal, radius 16 plus a black outline, so it overlaps the band and the icon's corner like a notification badge; shown while `Ui::toolRunning()` in Processing). Text cannot be drawn at an angle, so `prepareBadge()` draws the badge once per canvas size into a small sprite (`badge_`, internal RAM, freed by `setSize`), picking the largest DejaVu whose "EXT" fits the disc, and `toolMark` pushes it with a colour key: `pushSprite` at angle 0, `pushRotateZoomWithAA` otherwise. All four follow the tilt angle, gears included. All geometry is written in "128-space" and multiplied by `unit_ = size/128`, so a bigger canvas just scales. Static icons go through `rotated(x, y, angle, scale)` vertex by vertex, hence any angle and size; the gears take their own spin angle and ignore tilt. `gear(spin, GearStyle)` draws one of three variants via `gearBody`: `Working` (yellow), `Compacting` (grey), `Subagents` (a smaller main gear plus a 6-tooth satellite up-right, counter-rotating at the tooth ratio, the pair offset so its bounding box is centred). The two signs share `sign(body, angle, scale)`; `error` is the red mirror of `done` (circle + cross); `paused(angle, Hourglass)` is an animated hourglass: one curved glass wall is a polyline (`kWall`, top-left, mirrored four ways), `fillBulb(sy, ya, yb)` fan-fills any slice of a bulb between two heights, and the `Hourglass` phase (`drained`, `flip`, `settle`, `falling`) drives the top level, the dip, the stream, the growing pile with its peak, the 180° turn (added to the tilt angle) and the post-turn slide of the sand to the neck; white walls and amber frame bars go on top. Colours are `constexpr rgb565(r,g,b)`.

**Hook inspector** (`eventlog.h`, `eventview.h`, Tab5 only so far). `EventLog::push(HookEvent&&, nowMs)` keeps the last 16 with a sequence number and the receive time; `EventView::draw(log, statusLine, nowMs)` fills its canvas: header (title left, status right), the last event's `#seq name` in DejaVu24 with its age, then one row per field (key in grey in a 230 px column, value wrapped in white up to 3 lines, `...` when cut), then a history block of the last 8 as one-liners (`#seq age summary [project]`, the session id's first 8 chars when there is no `project` field) using the `summary` and `project` fields the daemon sends; the title of the last event carries `[project]` too. The board redraws it on every event, state change or once a second (ages). Pushing 1 MB from PSRAM each time is fine on the P4's DSI panel.

**State machine** (`ui.h`). `State {Idle, Processing, WaitingUser, Question, Error, Paused, Compacting, Off}`, classified by three predicates in `protocol.h`: `isAnimated` (Processing, Compacting, Paused: redrawn every frame; gears advance `kGearStep` 0.10 rad, the hourglass advances `animFrame_` through a 396-frame cycle = 12 s drain, 0.8 s eased 180° flip, 0.4 s settle, computed by `Ui::hourglass()`), `isStatic` (Idle, WaitingUser, Question, Error: drawn once, then on tilt change), `needsAttention` (WaitingUser, Question, Error: entry pulse of `AttentionConfig::frames` (60) frames, `1 + amp·|sin(πk/period)|` = three +10 % breaths over ~2 s, last frame forced to scale 1). `Ui::apply` redraws only on change and returns whether it changed. Subagents are a counter, not a state: `subagentStart`/`subagentStop` adjust it, `Processing` renders with `GearStyle::Subagents` while it is above zero, and it resets on Idle/Off/Error/Paused so a missed stop cannot leave a satellite behind; `toolStart`/`toolStop` set the tool-running flag (EXT badge, same reset rule); the work timer (`workFrames_`, advanced while Processing/Compacting, one ring lap = `kRingLapFrames` 18000 = 10 min) resets with it. `setSessions(codes)` stores up to 8 codes and redraws a static icon on change; dots appear from two sessions up. Link watchdog: `noteCommand()` resets `linkFrames_` on every line except `status`; `ping()` also arms it; `linkLost()` = armed and ≥ `kLinkLostFrames` (1800 ≈ 60 s) since the last line; `tick` redraws a static icon when the mark appears or disappears. `setTiltConfig` swaps the mapping and redraws. `setVisible(false)` makes `render` skip drawing (and remember it was skipped) so several `Ui`s can share a display; `setVisible(true)` redraws what was missed. `setSubagents`/`setToolRunning` are the absolute setters the per-session lines use. `feedAccel` redraws a static state when the tilt moved ≥ 1° since the last draw, but not while a pulse is running. `tick(screenOn)` does the per-frame work; the timers (`stateFrames_`, `linkFrames_`, `workFrames_`) always advance, but with the screen dark nothing is drawn and a pending pulse is dropped.

**Main loop timing** (board). No separate task or timer. The blocking `usb_serial_jtag_read_bytes` waits for what is left of a 33 ms frame (`kFrameUs`, `lastTickUs` from `esp_timer`), which paces the animations and the tilt filter at ~30 fps, and `Ui::tick(screenOn, frames)` is then given the number of frames that really went by (rounded), so every counter (`stateFrames_`, `linkFrames_`, `workFrames_`, `animFrame_`, the pulse, the gear angle) follows real time even when a frame takes longer: the Tab5's 486 px gear takes ~50 ms to draw and push, and a `screenshot` blocks the loop for ~17 s. Before this the Tab5's clocks and work ring ran at about half speed. A pass that returned early with data (frames 0) advances nothing. Constants are still written in frames at 30 fps; the AtomS3R uses the same scheme.

**Screen policy** (board). `main.cpp` derives the backlight from three inputs: `screenOn` (the button), `autoOff` (set after `kAutoOffFrames` = 30 min in Idle, or 30 min of `linkLost()`; cleared when `apply` reports a state change) and `ui.linkLost()` (dims to `kDimBrightness` 24 instead of 128). The button clears `autoOff` first; a second press toggles. `ui.tick()` gets the resulting on/off so it skips drawing while dark.

**Calibration storage** (`calibration.h`, used by both boards). On the AtomS3R the compiled defaults (`kBootRotationOffset` relative to the display default, `kTilt`) become a `Calibration {rotation, sign, offsetDeg}`; NVS (namespace `monitor`, keys `rot` u8, `sign` i8, `offset_mdeg` i32) overrides them at boot (`loadCalibration`), `calibrate` stores (`saveCalibration`, `reset` erases the namespace) and applies at once (`applyCalibration`: `setRotation` + `Ui::setTiltConfig`) and answers with `STATUS`. On the Tab5 the same record holds the `Orientation` offset and sign. `initCalibrationStorage` wraps `nvs_flash_init`; the default partition table has the `nvs` partition at `0x9000`. `idf.py flash`, the web flasher and a three-file `write_flash` leave it alone; the **merged image erases it** (`merge_bin` fills `0x9000`–`0x10000` with `0xFF`), so after flashing a merged image the boot log says `(compiled)` and the unit must be calibrated again.

**Auto-rotation** (`tilt.h`). Accelerometer (gravity vector), not the gyro, and continuous: `updateTilt` computes the icon angle as `angleSign * atan2(ay, ax) + angleOffset`, low-pass filters it (`smoothing` 0.25 per frame, wrap-aware), and reports the icon as stale once it has moved ≥ `redrawStep` (1°). Readings are ignored and the angle held when the module lies flat (`|az| > flatThreshold` 0.80) or the in-plane component is below `tiltThreshold` (0.40). The display stays at the boot rotation; only the drawing rotates. Calibration is per board: compiled defaults in its `main.cpp` (`kBootRotationOffset`, steps of 90° clockwise added to the display default; `TiltConfig::angleSign` / `angleOffset`), overridable per unit with `calibrate` (stored in NVS, see Calibration storage). M5Unified does not remap the BMI270 axes, so these are empirical; the AtomS3R values (rotation 1, sign −1, offset 0) were verified in all four standing positions and under continuous tilt. To recheck, stand the device on a side, send `status`, and compare `angle=` with what looks upright; `sign=`/`offset=`/`rot=` in the reply are the values in effect.

**Button** (board). On the AtomS3R, `BtnA` (under the screen) toggles backlight brightness 128/0; it does not change state. The Tab5 has no button in use: a tap wakes an auto-off screen, opens a tile's detail page or returns from it.

## Gotchas

- `freertos/FreeRTOS.h` must be included **before** `M5Unified.h` or the build fails with `#error include FreeRTOS.h must appear ...`.
- `sdkconfig` is gitignored; `firmware/<board>/sdkconfig.defaults` (generated with `idf.py save-defconfig`) holds the only non-defaults. For the AtomS3R: target `esp32s3` and **flash size 8 MB**. For the Tab5: target `esp32p4`, 16 MB QIO flash, PSRAM at 200 MHz with `CONFIG_IDF_EXPERIMENTAL_FEATURES`, 256 KB L2 cache, one large app partition, 16 KB main task stack. An existing `sdkconfig` keeps its old values when a default is added: edit it too (or delete it and reconfigure), as was done for the stack. Regenerate it with that command after changing anything in menuconfig that must persist. The console is UART0 primary with USB Serial/JTAG as secondary, which is the ESP-IDF default for the S3; that secondary channel is what makes logs visible over USB.
- The component manager resolves manifests from every component in the build, including `components/monitor-core`; `dependencies.lock` and `managed_components/` are still created in the project directory (`firmware/atoms3r/`). If the dependency ever looks missing, check that `EXTRA_COMPONENT_DIRS` in the project `CMakeLists.txt` points at `../../components`.
- ESP-IDF logs and the protocol share the same USB port. The host only writes (except for `status` and `version`), so it works, but a reply can arrive interleaved with log lines, and the unsolicited boot `VERSION` line can sit in the buffer — filter on the prefix you asked for (`Send-SerialCommand` in the daemon does). Long `ESP_LOGI` lines can be dropped on that channel; anything the host must see goes through `usb_serial_jtag_write_bytes`.
- The AtomS3R's backlight is driven by an I2C chip, not a GPIO; if the screen stays black with the code apparently running, suspect the M5Unified version (`^0.2`, locked at 0.2.21).
- The USB port can disappear for a few seconds after a reset or re-plug; a flash that fails with "could not open port" usually succeeds on retry. A flash that fails with "port is busy" means the daemon holds it: `POST /release` first.
- PowerShell: inside a double-quoted string `$name:` is parsed as a scoped variable; write `${name}:`. The daemon script died silently on exactly that once.
- The task runs the daemon through `conhost.exe --headless`. With Windows Terminal as the default terminal (`HKCU\Console\%%Startup` `DelegationConsole`/`DelegationTerminal`), a console started by the task is handed to a Terminal window that `-WindowStyle Hidden` does not hide; closing that window killed the daemon (`LastTaskResult` `0xC000013A`, no "daemon started" line in the log) and the hooks failed silently until the next logon. With conhost in between, `Stop-ScheduledTask` ends conhost only: the daemon watches its parent (`$script:launcher`, set when the parent is `conhost`) and leaves within 250 ms, and `Install-MonitorDaemon.ps1`'s `Stop-Daemon` waits for that and stops any leftover `Monitor-Daemon.ps1` process by command line. A daemon run by hand from a shell has no such parent and is unaffected.
- The scheduled task is registered with `MultipleInstances IgnoreNew`: re-registering while an instance runs leaves the old one (old arguments) in charge. `Install-MonitorDaemon.ps1` stops it first; if a manual `Register-ScheduledTask` seems to have no effect, that is why. And a device that is still booting when the daemon opens the port (the Tab5 needs ~2.5 s) misses the first `version`; the daemon asks again every 10 s until it has an answer.
- Claude Code rewrites `~/.claude/settings.json` itself (e.g. when it records a newly allowed directory or permission). A hooks block edited by hand during a live session can be lost in that rewrite; verify with `/hooks` or by re-reading the file, and re-apply if needed.
- `build/project_description.json` → `project_version` shows which `git describe` the current build carries; if it does not match the tag you are releasing, reconfigure (see Releasing). The same applies to `built=` in the `VERSION` reply: it is the compile time of ESP-IDF's app-descriptor object, refreshed on a reconfigure, not on every incremental build.
- `status` does not feed the link watchdog, on purpose: otherwise a status query would always report `link=ok`. To test the watchdog stop the daemon (`Stop-ScheduledTask "claude-monitor daemon"`), wait 75 s, open the port yourself and send `status`; expect `link=lost screen=dim`. Right after a reset the device reports `link=unarmed` until the first ping.
- Session dots need two or more sessions; a single session draws none. To see them without a second Claude Code, POST a fake hook (`{"hook_event_name":"UserPromptSubmit","session_id":"test"}`) to `/hook` and a `SessionEnd` for the same id afterwards.
- Tab5, verified 2026-09-11 on a unit with ESP32-P4 rev v1.3 and an ST7121 panel: the USB-C **is** the P4's USB Serial/JTAG (enumerates as VID 303A PID 1001, "USB Serial Device (COMx)" + "USB JTAG/serial debug unit", like the AtomS3R), so `idf.py -p COMx flash` needs no button and the `usb_serial_jtag` transport is right; a charge-only cable shows nothing at all. M5GFX needs `CONFIG_SPIRAM_SPEED_200M` (it logs "M5Tab5 need PSRAM SPEED 200MHz" and gives up otherwise), which ESP-IDF 5.5 only offers with `CONFIG_IDF_EXPERIMENTAL_FEATURES=y`; the boot log shows "esp_psram: Adding pool of 32768K", "[Autodetect] board_M5Tab5" and the panel line when it is right. The panel is 720×1280 native; `main.cpp` rotates to landscape when width < height. `M5Canvas::setPsram(true)` before `createSprite`, or the 450 KB / 1 MB sprites fail ("canvas allocation failed" in the log). The RISC-V GCC promotes `-Wformat-truncation` to an error where the Xtensa one warns: build both boards before pushing.
- Smooth (VLW) fonts in M5GFX, as the anime theme uses them: `setTextSize` scales a glyph by repeating or skipping whole source pixels, and skipping loses strokes (an O without its right column at 0.9×), hence `pick()` in `glyphs.cpp` prefers the size at or below and scales up (to 1.3×) before it scales a bigger one down; glyph width, advance and left offset are 8-bit in the format (`make-fonts.py` stops on a glyph that does not fit); `drawChar` `alloca`s the glyph (see the Tab5's stack); with a background colour different from the text colour it fills the whole cell (taller than a tight tag: `tag()` clips), without one it blends by reading the target back. A `setFont` on a canvas does not free our shared `VLWfont` objects; `loadFont` would replace a canvas's own runtime font, so it is not used.
- Changing the Tab5's partition table or stack: the existing `firmware/tab5/sdkconfig` keeps its old values; edit it as well (or move it away and `idf.py reconfigure`, which is what was done when `partitions.csv` came in). A board flashed with the new image but the old partition table does not boot the 1.6 MB app: always write the partition table too (`idf.py flash` and the three-part esptool line do).
- To see what the hooks deliver without a Tab5: `GET /events` on the daemon (the exact lines it would send) or run it with `-LogEvents` and read `hooks.jsonl`.
- The README's pictures come from the Tab5 itself (`tools/Make-ReadmeImages.ps1`, daemon stopped, board in landscape); regenerate them after changing an icon rather than editing the PNGs. The icon crop assumes the single-tile layout on 1280×720 (icon 486 px at (397,117)); if `applyLayout` or `textStyleFor` change, update `$icon` in the script.
