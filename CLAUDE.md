# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Firmware for M5Stack devices that act as a desk status light for Claude Code. Claude Code hooks send a one-word line over USB serial; the device draws the matching icon and keeps it upright as it is tilted. Native **ESP-IDF 5.5** (C++/CMake/FreeRTOS), no Arduino, no PlatformIO, no Wi-Fi; the host side is three PowerShell 7 scripts (a daemon that owns the port and receives the hooks over HTTP, its installer, and a one-shot sender). The first and reference board is the **AtomS3R** (ESP32-S3, 128×128 IPS display, BMI270 IMU); the layout is built so a second board (planned: Tab5, ESP32-P4) is another small project sharing the same component.

`claude-code-status-monitor-atoms3r.md` is the original write-up (design rationale, icon geometry, hook configuration) — read it before non-trivial changes. The code has since moved past it on purpose: the waiting icon shows an exclamation mark instead of the word STOP, there is a blue question-mark sign for `AskUserQuestion`, there are `error` (red cross), `paused` (amber hourglass) and `compacting` (grey gear) states plus a subagent counter that gives the gear a satellite, the "look at the terminal" signs pulse on entry, the static icons rotate continuously with the tilt instead of in 90° steps, there is a `status` command, the hook set covers far more than the article's four events, the code is split into a component plus per-board projects instead of one `main.cpp`, a band around the icon carries overlays (elapsed-work ring, session dots, lost-link mark), the host pings the device and the screen dims/switches off on its own, the calibration can be stored in NVS at runtime, and there are host tests and CI with a browser flasher. Do not "fix" those back toward the article's listing. The README's hooks section is the current reference for the host side, and `CHANGELOG.md` records what each release changed (keep it updated in the same commit as the change, under the next version).

Machine-specific notes (toolchain paths, COM port, antivirus) belong in `CLAUDE.local.md`, which is gitignored.

## Layout

- `components/monitor-core/` — everything board-independent, in namespace `monitor`: `protocol.h` (states, command parsing, `LineParser`, `kProtocolVersion`), `tilt.h` (accelerometer → icon angle, `TiltConfig`), `icons.h` (`Icons`: procedural drawing into an `M5Canvas`), `ui.h` (`Ui`: state machine, gear spin, entry pulse), `version.h` (`formatVersionLine`: the `VERSION` reply from ESP-IDF's app descriptor, chip info, flash size, uptime and reset reason, plus `boardModelName` for M5Unified's detected board; needs `PRIV_REQUIRES esp_app_format esp_hw_support esp_timer esp_system spi_flash`), `eventlog.h` (`EventLog`: the last hook event and a ring of previous ones, with the board's clock for ages), `eventview.h` (`EventView`: draws that log into an `M5Canvas` as a page, key/value rows wrapped, history at the bottom; lays itself out from the canvas size), `orientation.h` (`Orientation`: whole-display rotation in 90° steps from the accelerometer, with hysteresis and a hold time; host-tested), `calibration.h` (`Calibration` in NVS namespace `monitor`, keys `rot`/`sign`/`offset_mdeg`, `initCalibrationStorage`/`loadCalibration`/`saveCalibration`; the boards give the fields their meaning).
- `firmware/tab5/` — the ESP-IDF project for the M5Stack Tab5 (ESP32-P4): `main/main.cpp` is the multi-session view. `std::array<Slot, 6> slots` plus a `placeholder` slot; a `Slot` owns its PSRAM `M5Canvas`, `Icons`, `Ui` and `EventLog` (`place(size, x, y)` recreates the sprite when the size changes and calls `Icons::setSize`). `applyLayout()` (on session count change, rotation change, view change) hides every `Ui` (`setVisible(false)`), then either lays the grid (1 → 1×1, 2 → 2×1 or 1×2, 3–4 → 2×2, 5–6 → 3×2 or 2×3 by orientation; icon size = tile width − 32 capped by tile height − 2·`kTextBand` 52) or the detail page (icon 480 at (40,120) with the inspector at (560,0) in landscape; 400 at (160,80) with the inspector at (0,560) in portrait). `drawTexts()` writes the name (DejaVu24, white) above and the clock (`framesInState()/30` as mm:ss) below each visible tile straight on the display once a second; `drawInspector()` draws the detail slot's log. `session` lines create/update slots (`applyState` → `Ui::apply`, beep on WaitingUser/Error when the tile is visible, `setSubagents`, `setToolRunning`), `session_end`/`session_clear` free them (`Slot::reset`), `event` lines go to the slot named by `session_id` (creating it if the event beat its session line); the aggregate words drive the placeholder, shown only while no slot is used. Touch: `wasClicked()` with `tile.contains(x, y)` opens the detail, any tap on the detail returns, a tap wakes an auto-off screen. Beeps are `M5.Speaker.tone` two notes five frames apart (`Beep`/`tickBeep`), non-blocking. The BMI270 drives `Orientation` (whole display turns in 90° steps); the icon itself is never tilted. `calibrate rot=N sign=S` means "N is the upright rotation right now": the offset is `orient.offsetFor(N, S)`, stored in NVS as `rotation`/`sign` (`offsetDeg` unused); `calibrate reset` → the compiled defaults, offset 3 and sign 1, which were verified on one unit (with the tablet on its stand gravity reads along +x, sector 0, and the upright display is rotation 3; with offset 1 every position came out upside down). USB Serial/JTAG transport with an 8 KB receive buffer, `LineParser(4096)`, 512-byte reads; `kFeatures = "events,touch,rotate,sessions"`. `STATUS` reports the aggregate state of the visible tiles, `sessions=` as one code letter per tile, `rot=` (display rotation in effect), `angle=` (gravity direction in the panel plane), `offset=` (sector-0 rotation), `sector=`, `tiles=`, `view=grid|detail`. `sdkconfig.defaults`: `esp32p4`, 16 MB QIO flash, PSRAM 200 MHz + `CONFIG_IDF_EXPERIMENTAL_FEATURES`, L2 cache 256 KB, single large app partition. Runs on hardware (see Gotchas for what was verified).
- `tools/collect-images.sh` — names a build's images for a release and merges them using the project's `flasher_args.json`; CI runs it per board. Its `idf_component.yml` declares `m5stack/m5unified ^0.2` as a **public** dependency, because `icons.h` exposes `M5Canvas`.
- `firmware/atoms3r/` — the ESP-IDF project for the AtomS3R: `CMakeLists.txt` adds `../../components` via `EXTRA_COMPONENT_DIRS`; `main/main.cpp` holds only board wiring (canvas size, boot rotation and IMU calibration constants, `usb_serial_jtag` transport, `status` reply formatting, `BtnA` screen toggle, the 33 ms loop); `sdkconfig.defaults` carries the two non-defaults (target `esp32s3`, 8 MB flash); `dependencies.lock` pins the M5Unified/M5GFX versions and is tracked. Build artefacts (`build/`, `managed_components/`, `sdkconfig`, `.vscode/settings.json`) live here and are gitignored; `.vscode/c_cpp_properties.json` and `launch.json` are tracked.
- `host/Monitor-Daemon.ps1` — the host daemon (PowerShell 7): owns the serial port, receives Claude Code hook events as HTTP POSTs on `http://localhost:47831/hook`, keeps one state per session, sends the device the most urgent one, logs to `%LOCALAPPDATA%\claude-monitor\daemon.log`. `host/Install-MonitorDaemon.ps1` registers it as a logon scheduled task ("claude-monitor daemon"). `host/Send-ClaudeState.ps1` is the one-shot sender: through the daemon's `/state/<state>` when it runs, else straight to the port; it is also what the no-daemon command-hook variant calls.
- `claude-monitor.code-workspace` — multi-root workspace (repo + `firmware/atoms3r`) so the ESP-IDF extension finds a project.
- `tests/host/` — host tests for `protocol.cpp` and `tilt.cpp` (`test_core.cpp`, plain C++17, a `CHECK` macro, exit code = failures); `run.sh` (Linux/macOS/CI, `g++`) and `run.ps1` (Windows, MSVC via `vswhere`, else `g++`). The icons and `Ui` need `M5Canvas` and are not covered.
- `.github/workflows/build.yml` — CI: host tests + AtomS3R build (`espressif/esp-idf-ci-action`, ESP-IDF v5.5) on every push/PR, images as an artifact; on a `v*` tag, assets attached to the release (`softprops/action-gh-release`, which creates the release if it does not exist) and the web flasher deployed to GitHub Pages; `workflow_dispatch` with the `release` input republishes the flasher from an existing release's assets. `docs/index.html` is that page (ESP Web Tools; CI puts `manifest.json` and the **three parts** next to it, and replaces `__VERSION__`). The manifest deliberately lists bootloader/partition table/app at their offsets rather than the merged image: the merged image pads the gap over the NVS partition and would erase a stored calibration.
- `CHANGELOG.md` — one section per release. `.clangd` (strips `-f*`/`-m*` so clangd can read the xtensa compile database) and `.devcontainer/` (the stock `espressif/idf` image; inside it, work from `firmware/atoms3r`) are the only other tracked files besides the article, the README and the license.

A new board = a new `firmware/<board>/` project with its own `sdkconfig.defaults`, `main/main.cpp` and calibration constants, plus a section in the README. Anything that would be duplicated between boards belongs in `monitor-core`.

## Toolchain and commands

`idf.py` only exists inside an activated ESP-IDF environment: the VS Code command **ESP-IDF: Open ESP-IDF Terminal**, the "ESP-IDF PowerShell" Start Menu shortcut on Windows, or `export.ps1` / `export.sh` from the ESP-IDF directory. Never prefix `idf.py` with `bash` on Windows (it hands the line to WSL). Keep the project path free of spaces. Run from the board's project directory, or pass it with `-C`:

```
cd firmware/atoms3r
idf.py set-target esp32s3     # only on a fresh checkout or after fullclean
idf.py build                  # first build downloads M5Unified/M5GFX into managed_components/
idf.py -p COM5 flash          # esptool over the USB-C virtual serial port (/dev/ttyACM0 on Linux)
idf.py -p COM5 monitor        # Ctrl+] to exit. CLOSE IT before sending protocol commands: the port is exclusive on Windows
idf.py menuconfig
idf.py fullclean
```

The Tab5 project is `firmware/tab5` with `idf.py set-target esp32p4`; its first build downloads its own `managed_components/` and compiles the whole IDF for the P4 (minutes). Everything else is the same.

`idf.py flash` rebuilds first. A rebuild can take minutes on a machine whose antivirus scans the toolchain, so run it with a long timeout. **The daemon owns the port while it runs**: before `flash`, `monitor` or any direct serial access, `Invoke-RestMethod -Method Post http://localhost:47831/release` (the port is free for 120 s, then the daemon reconnects and re-sends the current state; `POST /reconnect` reconnects at once). Without the release, flashing fails with "port is busy". First-ever flash of a board may require holding the side reset button ~2 s to enter download mode. The VS Code extension is configured with `idf.flashType: JTAG` (OpenOCD, `board/esp32s3-builtin.cfg`), so **ESP-IDF: Flash your Project** goes over the S3's built-in USB-JTAG instead; both paths use the same cable. The binary is `build/claude-monitor-atoms3r.bin`.

Manual end-to-end test (device flashed, monitor closed):

```powershell
.\host\Send-ClaudeState.ps1 -State processing -PortName COM5   # also: waiting_user | question | error | paused | compacting | idle | off | subagent_start | subagent_stop
```

Reading the device's replies: with the daemon running, `Invoke-RestMethod http://localhost:47831/serial/status` returns the `STATUS` line, `Invoke-RestMethod http://localhost:47831/version` the `VERSION` line parsed (hardware model, firmware version, uptime), and `GET /status` shows sessions and the last state sent. Without the daemon, open `System.IO.Ports.SerialPort` on the port at 115200 with DTR/RTS off, `WriteLine("status")`, then `ReadLine()` until a line containing `STATUS` — boot-log fragments may precede it. Note that in a session where the hooks are active, every tool call that prompts for permission sends `waiting_user` before it runs, so a status read taken from Claude Code will usually report that state rather than the one you set a moment earlier; the daemon log shows the exact sequence.

Tests: `.\tests\host\run.ps1` (Windows) or `bash tests/host/run.sh`; they take seconds and need no ESP-IDF. Run them after touching `protocol.*` or `tilt.*`, and add a `CHECK` for every new protocol word or parsing rule. There is no linter. `.clangd` (repo root) strips `-f*`/`-m*` flags so clangd can parse the xtensa compile database; `firmware/atoms3r/.vscode/settings.json` (gitignored, machine-specific: ESP-IDF setup, clangd binary and `--compile-commands-dir`, COM port) points it at `firmware/atoms3r/build`. `firmware/atoms3r/.vscode/c_cpp_properties.json` is tracked and carries an absolute `compilerPath`.

## Releasing

A version is an annotated tag `vX.Y.Z` on `main` plus a GitHub release with four images per board (`claude-monitor-<board>-vX.Y.Z{,-merged,-bootloader,-partition-table}.bin`, produced by `tools/collect-images.sh`; releases up to 1.2.0 used plain `bootloader.bin` / `partition-table.bin` for the AtomS3R), and CI does the build for every board in the matrix: write the `CHANGELOG.md` section, commit, `git tag -a vX.Y.Z`, push the tag, wait for the `build` workflow (`gh run watch`), which attaches the images to the release for the tag (creating the release if none exists) and deploys the web flasher; then put the notes in with `gh release edit vX.Y.Z --title "claude-monitor X.Y.Z" --notes-file notes.md`. Notes follow the existing releases (new on the device, new on the host, flashing without the toolchain, built with). Check the `fw=` the CI image reports (the workflow log prints the embedded version) before flashing it to the reference unit.

Local fallback, same result by hand: the version embedded in the binary (`esp_app_desc`, printed as `App version:` in the boot log and as `fw=` in `STATUS`) is `git describe --tags --dirty`, **captured when CMake configures**, not on every build: tag first, make sure the tree is clean, then `idf.py reconfigure build`. A plain `idf.py build` after tagging keeps the previous string (the 1.1.0 assets had to be rebuilt for exactly that reason). Then, in the activated ESP-IDF shell (its venv provides `esptool`):

```powershell
cd firmware/atoms3r
python -m esptool --chip esp32s3 merge_bin -o claude-monitor-atoms3r-vX.Y.Z-merged.bin --flash_mode dio --flash_freq 80m --flash_size 8MB 0x0 build/bootloader/bootloader.bin 0x8000 build/partition_table/partition-table.bin 0x10000 build/claude-monitor-atoms3r.bin
Copy-Item build/claude-monitor-atoms3r.bin claude-monitor-atoms3r-vX.Y.Z.bin
gh release create vX.Y.Z --title "claude-monitor X.Y.Z" --notes-file notes.md claude-monitor-atoms3r-vX.Y.Z-merged.bin claude-monitor-atoms3r-vX.Y.Z.bin build/bootloader/bootloader.bin build/partition_table/partition-table.bin
```

The flash arguments come from `build/flasher_args.json`. `gh release upload vX.Y.Z --clobber <files>` replaces assets on an existing release. GitHub Pages is set to the "GitHub Actions" source (`gh api repos/icefoxj/claude-monitor/pages` shows `build_type: workflow`), and the `github-pages` environment has custom deployment-branch policies for `main` and the tag pattern `v*` (without the `v*` entry a tag build fails with "not allowed to deploy to github-pages due to environment protection rules"). The flasher page is republished by a tag build or by `gh workflow run build.yml -f release=vX.Y.Z`.

## Architecture

**Serial protocol** (`protocol.h`). One command per line, `\n`-terminated. State commands: `processing`, `waiting_user`, `question`, `error`, `paused`, `compacting`, `idle`, `off`. Counter commands: `subagent_start` / `subagent_stop`. Flag commands: `tool_start` / `tool_stop` (a tool process is running; `STATUS` shows `tool=`). `sessions <codes>`: the live sessions as one letter each (`sessionCode()`: p w q e h c i), most urgent first, up to 8 used. `ping`: heartbeat. `calibrate rot=<0-3> sign=<1|-1> offset=<deg>` (any subset) or `calibrate reset`, parsed by `parseCalibration` into a `CalibrationRequest`; a bad field rejects the whole line and the board answers `ERROR calibrate: …`. And `status`, answered with one `STATUS state=… subagents=… rot=… angle=… ax=… ay=… az=… fw=… board=… sign=… offset=… sessions=… link=… work=… screen=…` line (`fw` is `esp_app_get_description()->version`, `link` is `unarmed|ok|lost`, `work` is seconds of processing this turn, `screen` is `on|dim|off`). And `version`, answered with one `VERSION board=… model=… chip=… rev=… cores=… flash=… fw=… idf=… m5unified=… protocol=… project=… built=… sha=… uptime=… reset=…` line (`board` = the build's `kBoard`, `model` = `boardModelName(M5.getBoard())`, so a firmware on the wrong module shows up; `protocol` = `kProtocolVersion`, bump it when words are added). The board also sends the `VERSION` line once at boot, right after `usb_serial_jtag_driver_install`, through the driver: an `ESP_LOGI` of it was lost, because the console's secondary USB channel drops long lines when the host is not draining the FIFO. Neither `status` nor `version` feeds the link watchdog. `VERSION` carries `features=` (comma list; `-` for none): a capability the host checks before sending anything optional. Protocol 3 adds `event <name>\t<key>=<value>\t…` (`parseEventLine` → `HookEvent {name, fields}`, `HookEvent::find`): a whole hook event, sent only to a device whose features include `events`, because a line can be a few KB and the AtomS3R's 1 KB receive buffer and 64-byte `LineParser` would choke on it (its parser now drops an over-long line whole, newline included, so nothing leaks through as a stray word). Protocol 5 adds the per-session lines for boards with `sessions` in features: `session <id>\tlabel=…\tstate=…\tsubagents=…\ttool=…\tproject=…\troot=…` (same tab format, parsed with `parseEventLine`, the state with `parseState`), `session_end <id>`, `session_clear`. When adding a word, bump `kProtocolVersion` and add a `CHECK` in the host tests. `parseCommand` splits the first word from the argument (`ParsedCommand::arg`); `LineParser` strips trailing `\r`/spaces and discards lines over 64 bytes; unknown words are ignored. The transport is the board's: on the AtomS3R it is the ESP32-S3's native **USB Serial/JTAG** peripheral (no UART bridge chip; opening the port does not reset the board), and the `STATUS` reply is written straight through that driver so it does not depend on where the ESP-IDF console is routed. The hook → state mapping (which events, which `Notification` types and `StopFailure` error types go where) lives in `Map-Event` in `host/Monitor-Daemon.ps1` and is documented as a table in the README's hooks section; the no-daemon variant expresses the same mapping as matchers in `settings.json`. When a state is added, update `Map-Event`, the README table, the no-daemon JSON and `Send-ClaudeState.ps1`'s `ValidateSet`. There is no hook event for the moment a permission is approved; the daemon infers it from the tool's process starting (see Host daemon), and without that `waiting_user` lasts until the approved tool's `PostToolUse`.

**Host daemon** (`host/Monitor-Daemon.ps1`). `~/.claude/settings.json` has one identical HTTP hook (`{"type": "http", "url": "http://localhost:47831/hook", "timeout": 2, "headers": {"X-Claude-Project": "${CLAUDE_PROJECT_DIR}"}, "allowedEnvVars": ["CLAUDE_PROJECT_DIR"]}`) for the fourteen events of interest (SessionStart, UserPromptSubmit, PreToolUse for every tool, PostToolUse, PostToolUseFailure, PostToolBatch, Notification, Stop, StopFailure, PreCompact, PostCompact, SubagentStart, SubagentStop, SessionEnd); the daemon reads `hook_event_name`, `session_id` and the event's detail fields. Per session it keeps `state`, `subagents`, `last`; the device gets the highest-priority state among live sessions (`$Priority`: error 6 > waiting_user = question 5 > paused 4 > compacting 3 > processing 2 > idle 1 > off 0, ties → most recent), sent only on change, plus `subagent_start`/`subagent_stop` deltas to keep the device's counter equal to the sum over sessions, plus `sessions <codes>` when the code string changes (`Sync-Device`). `SessionEnd` removes the session; the last one leaving sends `off`; sessions silent for `SessionTimeoutMinutes` (240) expire. **Approval detection**: on a session's first hook (or when its known process is gone) `Resolve-ClientPid` reads the request's TCP connection (`Get-NetTCPConnection -LocalPort <client port> -RemotePort 47831`, only valid while the request is being handled) to learn the session's `claude.exe` PID; `Register-ProcessEvents` subscribes to WMI `__InstanceCreationEvent`/`__InstanceDeletionEvent` on `Win32_Process` (WITHIN 0.5, works without admin) and `Update-ProcessEvents`, called every main-loop pass, matches them: a child of a session's PID (not `conhost.exe`) starting while the session is `waiting_user` flips it to `processing` and is kept in `tools` (pid → name); a tool process ending leaves `tools`; the session PID ending marks it `dead` and `Expire-Sessions` drops it (the transcript-mtime heuristic only applies to sessions without a PID). `Sync-Device` sends `tool_start`/`tool_stop` when "the shown session has a live tool process" changes (`deviceTool`, reset like subagents), and ends with `Send-SessionLines`: for a device with `sessions` in features, `session_end` for ids it had that are gone, then one `session` line per live session whose line changed (`Format-SessionLine`, cached in `deviceSessionLines`; `Get-SessionLabel` appends `#n` when several live sessions share a project, numbered by `first`), starting with `session_clear` on a forced sync. `Process-Hook` sends the event line only after `Sync-Device`, so a new session's tile exists before its first event; ignored events send it directly. `PostToolUse`/`PostToolUseFailure` purge dead tool PIDs the events have not reported yet, and `subagent_start`/`stop` from a waiting session also mean approval. Everything degrades to hooks-only when WMI or the PID lookup is unavailable (`process_events` in `/status`). The main loop sends `ping` every `PingSeconds` (30) while the port is open. The port is reopened every 2 s when lost; on (re)connect the daemon asks `version` first (`Read-DeviceInfo`, kept as `device_info` in `GET /status`, also served fresh by `GET /version`) and then re-sends everything (state, subagents, sessions, a ping). The session's project comes from the `X-Claude-Project` request header (the hooks send `${CLAUDE_PROJECT_DIR}` with `allowedEnvVars`; `cwd` is not used when the header is there, because it follows the shell's `cd`), falling back to the first event's `cwd`; the name is the root's folder name unless `projects.json` (`-ProjectsPath`, `{ "root": "name" }`, reloaded by housekeeping when its mtime changes) says otherwise (`Get-ProjectName`). Every hook, mapped or ignored, also becomes an `event` line (`Format-EventLine`: `summary=<tag>`, `project=`, `project_root=`, then every top-level field in payload order, objects flattened one level, values one-lined and cut at `EventValueMax` 160, line capped at 3800) kept in a 50-entry ring for `GET /events` and written to the port only if `device_info.features` contains `events` (`Send-Event`); `-LogEvents` appends the raw payload as JSON lines to `EventLogPath` (`hooks.jsonl`, rotated at 20 MB). The port is opened with UTF-8 encoding so those lines survive. `POST /release` closes the port for a flash window; `POST /calibrate?rot=&sign=&offset=|reset=1` composes the `calibrate` line and returns the device's reply (`Send-SerialCommand` waits for `STATUS` or `ERROR` after `status` and `calibrate`). `Send-ClaudeState.ps1` must always `exit 0` because hook exit code 2 blocks Claude Code, and it retries a busy port for the no-daemon case.

**Rendering** (`icons.h`). `Icons` draws into a square 16-bpp `M5Canvas` supplied by the board (128×128 = 32 KB internal RAM on the AtomS3R). A frame is composed by `Ui::render`: one icon call (which clears the canvas), then the overlays, then `Icons::push()` (`pushSprite` at a configurable origin) — the icon functions themselves do not push, and nothing draws straight to `M5.Display`, which flickers. Icons are procedural (triangle fans, `thickLine` = oriented rect + two round caps, `thickArc` = polyline of those, one segment per ~6°), no bitmaps. The overlays live on a band of radius 60 (128-space), just outside the icons' 58: `ring(angle, fraction, lap)` grows clockwise from the top (lap 0 yellow, 1 amber, 2 red, each over the full ring of the previous lap, ≥3 full red); `sessionDots(angle, codes)` puts one 3.5-radius dot per code along the bottom, 10° apart, coloured by state (w and e both red) with a black outline so they read over the ring; `linkLost(angle)` is a hollow grey circle at the top; `toolMark(angle)` a solid blue dot on the right (shown while `Ui::toolRunning()` in Processing). All three follow the tilt angle, gears included. All geometry is written in "128-space" and multiplied by `unit_ = size/128`, so a bigger canvas just scales. Static icons go through `rotated(x, y, angle, scale)` vertex by vertex, hence any angle and size; the gears take their own spin angle and ignore tilt. `gear(spin, GearStyle)` draws one of three variants via `gearBody`: `Working` (yellow), `Compacting` (grey), `Subagents` (a smaller main gear plus a 6-tooth satellite up-right, counter-rotating at the tooth ratio, the pair offset so its bounding box is centred). The two signs share `sign(body, angle, scale)`; `error` is the red mirror of `done` (circle + cross); `paused(angle, Hourglass)` is an animated hourglass: one curved glass wall is a polyline (`kWall`, top-left, mirrored four ways), `fillBulb(sy, ya, yb)` fan-fills any slice of a bulb between two heights, and the `Hourglass` phase (`drained`, `flip`, `settle`, `falling`) drives the top level, the dip, the stream, the growing pile with its peak, the 180° turn (added to the tilt angle) and the post-turn slide of the sand to the neck; white walls and amber frame bars go on top. Colours are `constexpr rgb565(r,g,b)`.

**Hook inspector** (`eventlog.h`, `eventview.h`, Tab5 only so far). `EventLog::push(HookEvent&&, nowMs)` keeps the last 16 with a sequence number and the receive time; `EventView::draw(log, statusLine, nowMs)` fills its canvas: header (title left, status right), the last event's `#seq name` in DejaVu24 with its age, then one row per field (key in grey in a 230 px column, value wrapped in white up to 3 lines, `...` when cut), then a history block of the last 8 as one-liners (`#seq age summary [project]`, the session id's first 8 chars when there is no `project` field) using the `summary` and `project` fields the daemon sends; the title of the last event carries `[project]` too. The board redraws it on every event, state change or once a second (ages). Pushing 1 MB from PSRAM each time is fine on the P4's DSI panel.

**State machine** (`ui.h`). `State {Idle, Processing, WaitingUser, Question, Error, Paused, Compacting, Off}`, classified by three predicates in `protocol.h`: `isAnimated` (Processing, Compacting, Paused: redrawn every frame; gears advance `kGearStep` 0.10 rad, the hourglass advances `animFrame_` through a 396-frame cycle = 12 s drain, 0.8 s eased 180° flip, 0.4 s settle, computed by `Ui::hourglass()`), `isStatic` (Idle, WaitingUser, Question, Error: drawn once, then on tilt change), `needsAttention` (WaitingUser, Question, Error: entry pulse of `AttentionConfig::frames` (60) frames, `1 + amp·|sin(πk/period)|` = three +10 % breaths over ~2 s, last frame forced to scale 1). `Ui::apply` redraws only on change and returns whether it changed. Subagents are a counter, not a state: `subagentStart`/`subagentStop` adjust it, `Processing` renders with `GearStyle::Subagents` while it is above zero, and it resets on Idle/Off/Error/Paused so a missed stop cannot leave a satellite behind; `toolStart`/`toolStop` set the tool-running flag (blue dot, same reset rule); the work timer (`workFrames_`, advanced while Processing/Compacting, one ring lap = `kRingLapFrames` 18000 = 10 min) resets with it. `setSessions(codes)` stores up to 8 codes and redraws a static icon on change; dots appear from two sessions up. Link watchdog: `noteCommand()` resets `linkFrames_` on every line except `status`; `ping()` also arms it; `linkLost()` = armed and ≥ `kLinkLostFrames` (1800 ≈ 60 s) since the last line; `tick` redraws a static icon when the mark appears or disappears. `setTiltConfig` swaps the mapping and redraws. `setVisible(false)` makes `render` skip drawing (and remember it was skipped) so several `Ui`s can share a display; `setVisible(true)` redraws what was missed. `setSubagents`/`setToolRunning` are the absolute setters the per-session lines use. `feedAccel` redraws a static state when the tilt moved ≥ 1° since the last draw, but not while a pulse is running. `tick(screenOn)` does the per-frame work; the timers (`stateFrames_`, `linkFrames_`, `workFrames_`) always advance, but with the screen dark nothing is drawn and a pending pulse is dropped.

**Main loop timing** (board). No separate task or timer. `usb_serial_jtag_read_bytes(..., pdMS_TO_TICKS(33))` is both the blocking read and the ~30 fps clock for the animations, the tilt filter and every frame counter (the real rate is a little under 30 fps, so "60 s" constants run slightly long). Anything added to the loop must stay well under 33 ms.

**Screen policy** (board). `main.cpp` derives the backlight from three inputs: `screenOn` (the button), `autoOff` (set after `kAutoOffFrames` = 30 min in Idle, or 30 min of `linkLost()`; cleared when `apply` reports a state change) and `ui.linkLost()` (dims to `kDimBrightness` 24 instead of 128). The button clears `autoOff` first; a second press toggles. `ui.tick()` gets the resulting on/off so it skips drawing while dark.

**Calibration storage** (`calibration.h`, used by both boards). On the AtomS3R the compiled defaults (`kBootRotationOffset` relative to the display default, `kTilt`) become a `Calibration {rotation, sign, offsetDeg}`; NVS (namespace `monitor`, keys `rot` u8, `sign` i8, `offset_mdeg` i32) overrides them at boot (`loadCalibration`), `calibrate` stores (`saveCalibration`, `reset` erases the namespace) and applies at once (`applyCalibration`: `setRotation` + `Ui::setTiltConfig`) and answers with `STATUS`. On the Tab5 the same record holds the `Orientation` offset and sign. `initCalibrationStorage` wraps `nvs_flash_init`; the default partition table has the `nvs` partition at `0x9000`. `idf.py flash`, the web flasher and a three-file `write_flash` leave it alone; the **merged image erases it** (`merge_bin` fills `0x9000`–`0x10000` with `0xFF`), so after flashing a merged image the boot log says `(compiled)` and the unit must be calibrated again.

**Auto-rotation** (`tilt.h`). Accelerometer (gravity vector), not the gyro, and continuous: `updateTilt` computes the icon angle as `angleSign * atan2(ay, ax) + angleOffset`, low-pass filters it (`smoothing` 0.25 per frame, wrap-aware), and reports the icon as stale once it has moved ≥ `redrawStep` (1°). Readings are ignored and the angle held when the module lies flat (`|az| > flatThreshold` 0.80) or the in-plane component is below `tiltThreshold` (0.40). The display stays at the boot rotation; only the drawing rotates. Calibration is per board: compiled defaults in its `main.cpp` (`kBootRotationOffset`, steps of 90° clockwise added to the display default; `TiltConfig::angleSign` / `angleOffset`), overridable per unit with `calibrate` (stored in NVS, see Calibration storage). M5Unified does not remap the BMI270 axes, so these are empirical; the AtomS3R values (rotation 1, sign −1, offset 0) were verified in all four standing positions and under continuous tilt. To recheck, stand the device on a side, send `status`, and compare `angle=` with what looks upright; `sign=`/`offset=`/`rot=` in the reply are the values in effect.

**Button** (board). On the AtomS3R, `BtnA` (under the screen) toggles backlight brightness 128/0; it does not change state.

## Gotchas

- `freertos/FreeRTOS.h` must be included **before** `M5Unified.h` or the build fails with `#error include FreeRTOS.h must appear ...`.
- `sdkconfig` is gitignored; `firmware/<board>/sdkconfig.defaults` (generated with `idf.py save-defconfig`) holds the only non-defaults. For the AtomS3R: target `esp32s3` and **flash size 8 MB**. Regenerate it with that command after changing anything in menuconfig that must persist. The console is UART0 primary with USB Serial/JTAG as secondary, which is the ESP-IDF default for the S3; that secondary channel is what makes logs visible over USB.
- The component manager resolves manifests from every component in the build, including `components/monitor-core`; `dependencies.lock` and `managed_components/` are still created in the project directory (`firmware/atoms3r/`). If the dependency ever looks missing, check that `EXTRA_COMPONENT_DIRS` in the project `CMakeLists.txt` points at `../../components`.
- ESP-IDF logs and the protocol share the same USB port. The host only writes (except for `status` and `version`), so it works, but a reply can arrive interleaved with log lines, and the unsolicited boot `VERSION` line can sit in the buffer — filter on the prefix you asked for (`Send-SerialCommand` in the daemon does). Long `ESP_LOGI` lines can be dropped on that channel; anything the host must see goes through `usb_serial_jtag_write_bytes`.
- The AtomS3R's backlight is driven by an I2C chip, not a GPIO; if the screen stays black with the code apparently running, suspect the M5Unified version (`^0.2`, locked at 0.2.21).
- The USB port can disappear for a few seconds after a reset or re-plug; a flash that fails with "could not open port" usually succeeds on retry. A flash that fails with "port is busy" means the daemon holds it: `POST /release` first.
- PowerShell: inside a double-quoted string `$name:` is parsed as a scoped variable; write `${name}:`. The daemon script died silently on exactly that once.
- The scheduled task is registered with `MultipleInstances IgnoreNew`: re-registering while an instance runs leaves the old one (old arguments) in charge. `Install-MonitorDaemon.ps1` stops it first; if a manual `Register-ScheduledTask` seems to have no effect, that is why. And a device that is still booting when the daemon opens the port (the Tab5 needs ~2.5 s) misses the first `version`; the daemon asks again every 10 s until it has an answer.
- Claude Code rewrites `~/.claude/settings.json` itself (e.g. when it records a newly allowed directory or permission). A hooks block edited by hand during a live session can be lost in that rewrite; verify with `/hooks` or by re-reading the file, and re-apply if needed.
- `build/project_description.json` → `project_version` shows which `git describe` the current build carries; if it does not match the tag you are releasing, reconfigure (see Releasing). The same applies to `built=` in the `VERSION` reply: it is the compile time of ESP-IDF's app-descriptor object, refreshed on a reconfigure, not on every incremental build.
- `status` does not feed the link watchdog, on purpose: otherwise a status query would always report `link=ok`. To test the watchdog stop the daemon (`Stop-ScheduledTask "claude-monitor daemon"`), wait 75 s, open the port yourself and send `status`; expect `link=lost screen=dim`. Right after a reset the device reports `link=unarmed` until the first ping.
- Session dots need two or more sessions; a single session draws none. To see them without a second Claude Code, POST a fake hook (`{"hook_event_name":"UserPromptSubmit","session_id":"test"}`) to `/hook` and a `SessionEnd` for the same id afterwards.
- Tab5, verified 2026-09-11 on a unit with ESP32-P4 rev v1.3 and an ST7121 panel: the USB-C **is** the P4's USB Serial/JTAG (enumerates as VID 303A PID 1001, "USB Serial Device (COMx)" + "USB JTAG/serial debug unit", like the AtomS3R), so `idf.py -p COMx flash` needs no button and the `usb_serial_jtag` transport is right; a charge-only cable shows nothing at all. M5GFX needs `CONFIG_SPIRAM_SPEED_200M` (it logs "M5Tab5 need PSRAM SPEED 200MHz" and gives up otherwise), which ESP-IDF 5.5 only offers with `CONFIG_IDF_EXPERIMENTAL_FEATURES=y`; the boot log shows "esp_psram: Adding pool of 32768K", "[Autodetect] board_M5Tab5" and the panel line when it is right. The panel is 720×1280 native; `main.cpp` rotates to landscape when width < height. `M5Canvas::setPsram(true)` before `createSprite`, or the 450 KB / 1 MB sprites fail ("canvas allocation failed" in the log). The RISC-V GCC promotes `-Wformat-truncation` to an error where the Xtensa one warns: build both boards before pushing.
- To see what the hooks deliver without a Tab5: `GET /events` on the daemon (the exact lines it would send) or run it with `-LogEvents` and read `hooks.jsonl`.
